# Stabler — Security Hardening (deploy reference)

Companion to the deploy procedure in `CLAUDE.md`. Covers the security audit
outcome, the rate-limit code already shipped, and the three server-side steps
that must be applied by whoever runs the deploy (they are **config/settings, not
code** — they do not live in this repo).

Target prod site: **anjan.erpstable.com** on `ice-production`
(`/home/frappe/frappe-bench`, shared bench, ~22 tenants).

---

## Audit summary (June 2026)

| Area | Verdict | Notes |
|------|---------|-------|
| SQL injection | **Clean** | Every `frappe.db.sql` f-string interpolates only code-built clause strings or allow-listed constants; all user values use `%(name)s` parameters. |
| Input validation | **Good** | Whitelisted endpoints use `_require_company`, `has_permission`/`_assert_can_read/_write`, `cint`/`flt`/`getdate`, and enum allow-lists. |
| Secrets | **Good** | No hardcoded secrets; none logged. Timepay tokens stored as encrypted `Password` fields (`get_password`); payment secrets via `require_conf`. Frontends gitignore `.env*`. |
| Guest endpoints | **Gated** | 8 `allow_guest` endpoints: payment webhooks verify provider signatures; kiosk logins have per-IP brute-force limits + masked logging. |
| Rate limiting | **Was the gap** | App-level limiting only existed on kiosk login. Now extended (below) + needs the global backstop in steps 1–3. |

Minor follow-ups noted in the audit (not blocking): `save_lead` uses
`doc.update(parse_json(data))` (mass-assignment; relies on Frappe perms — an
allow-list of writable fields would be safer), and rotate the Timepay refresh
token per the anjan-hr notes.

## Code already shipped (in this release)

`@frappe.rate_limit` decorators (per-IP, 60s windows). These are `.py` changes —
they take effect on `bench restart`:

| Endpoint | Limit / 60s | Rationale |
|----------|-------------|-----------|
| `stabler.api.search.palette_search` | 120 | High-frequency per-keystroke; ceiling kept generous for shared office IPs. |
| `stabler.api.money.run_report` | 60 | Heavy query. |
| `stabler.api.money.export_report` | 30 | Heaviest, least frequent. |
| uzpay `click` / `payme` / `uzum` `merchant_endpoint` | 600 | DoS backstop only; signature stays the primary gate (provider callbacks come from few IPs at volume, so the ceiling is deliberately high). |
| arca `handle_payment_webhook` | 600 | Same as above. |

Note: the limiter buckets by client IP. Behind office NAT, users share an IP —
which is why the browser-endpoint limits are generous.

## Step 1 — Frappe per-site rate limit (safest, no nginx risk)

Add to `/home/frappe/frappe-bench/sites/anjan.erpstable.com/site_config.json`:

```json
"rate_limit": {
  "window": 3600,
  "limit": 3600
}
```

**Semantics caveat:** Frappe's global limiter is **duration-based, not
count-based** — `limit` is the cumulative request-processing *seconds* allowed
per IP per `window` seconds. The values above give each IP 3600s of processing
time per hour, throttling only a sustained abuser. Verify the key name against
your Frappe 16 build first (semantics shift between versions).

Apply:

```bash
bench --site anjan.erpstable.com clear-cache
```

(No restart needed for `site_config.json`.)

## Step 2 — nginx count-based limit (optional, harder ceiling)

```nginx
# http { } context — standalone file under /etc/nginx/conf.d/ (survives bench regen):
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=20r/s;

# inside the server { } block for anjan.erpstable.com, in the /api/ location:
location /api/ {
    limit_req zone=api_limit burst=40 nodelay;
    limit_req_status 429;
    # ...existing proxy_pass to the frappe socket stays...
}
```

**Caveat (shared bench):** the frappe nginx config is generated by
`bench setup nginx`; a manual edit to the *generated* file is overwritten on
regeneration. Put the `limit_req_zone` in a standalone `/etc/nginx/conf.d/*.conf`
(http context, persists), and add the `limit_req` line into the bench nginx
**template** (`config/templates/nginx.conf`) rather than the generated file.

Apply:

```bash
nginx -t && systemctl reload nginx
```

20r/s + burst 40 is generous for an office; lower for a tighter cap.

## Step 3 — Login brute-force throttle (a setting, confirm it's on)

UI: **System Settings → Security** → set **"Allow Consecutive Login Attempts"**
(e.g. 5) and **"Allow Login After Fail"** (e.g. 60 seconds).

Or via console:

```bash
bench --site anjan.erpstable.com console
```
```python
ss = frappe.get_single("System Settings")
ss.allow_consecutive_login_attempts = 5
ss.allow_login_after_fail = 60
ss.save(); frappe.db.commit()
```

Locks an IP out for 60s after 5 failed logins.

---

## Recommended order

1. **Step 1** + **Step 3** — zero infra risk, per-site, do these first.
2. **Step 2** — only if you want the harder count-based ceiling and are
   comfortable editing the bench nginx template.

The shipped code (rate-limit decorators) needs only the `bench restart` that is
already part of the standard deploy — no migrate, no build.
